AlpacApps Infrastructure Q&A

Honest, detailed answers about the scaffold's architecture, coupling, and fit for a multi-tenant social platform.

April 2026

alpacapps-infra

The template repo — what you'd actually clone. Answers scoped to the reusable scaffold only, excluding project-specific features.

What ships in the template vs. the full app?

alpacapps-infra is a standalone template repo (github.com/rsonnad/alpacapps-infra) that projects clone and diverge from. It includes:

  • 3 core services: GitHub Pages (hosting), Supabase (DB + auth + edge functions), Claude Code (dev agent)
  • ~10 core tables: app_users, user_invitations, property_config, brand_config, spaces, people, assignments, media, document_index, role_permissions
  • Centralized API: Single /api edge function with resource+action routing and role-based permission checks
  • Shared services: auth.js, config-loader.js, feature-registry.js, admin-shell.js, resident-shell.js, supabase.js
  • Feature flag system: 8 core flags (always-on) + 13 optional flags (config-driven)
  • Optional integrations: Stripe, Square, Resend (email), Telnyx (SMS), SignWell (e-sign) — deployed only if enabled

NOT in the template (project-specific): all IoT device tables (Tesla, Govee, Nest, LG, Anova, Glowforge), 3D property digital twin (PostGIS), native mobile apps, Discord/Telegram bots, Home Assistant, Airbnb sync, Vapi voice calling, Brave Search, PAI art generation, OpenClaw gateway.

The template is genuinely lean — ~10 tables, one API edge function, auth+config shell. Everything else is opt-in.
Is there a documented "clean base" profile in the template?

Yes — the template IS the clean base. Unlike the full app (which has 37+ migrations), the template ships a bootstrap schema with just the core tables. An interactive setup wizard (infra/index.html) and infrastructure guide (docs/alpacappsinfra.html) walk you through enabling each optional service.

The template also has an upgrade mechanism: projects track infra-upstream as a git remote, allowing selective pulls of new infrastructure features without overwriting project-specific code.

Unlike the full app, the template has an explicit separation. You clone, configure, diverge.
How coupled is the template to PM vocabulary and single-tenant patterns?

The template still uses PM-origin naming: spaces (rental units), people (tenants), assignments (bookings). And config tables are singletons (id=1). This reflects the template's origin as a property management scaffold.

However, the coupling is shallower than the full app:

  • The centralized API pattern, feature flag system, brand config, and auth shell are domain-agnostic
  • Edge function patterns (webhook ingestion, payment processing, email templates) are reusable with different table names
  • The feature-registry.js toggle system means you can disable entire PM modules at the config level
  • An orgs table has been added in recent architecture work (multi-tenant prep)
Verdict: You'd still rename tables and refactor singletons to per-org. But it's 1-2 days of work on the template, not the week+ it would be on the full app.
Could I use alpacapps-infra as the starting point for a social platform?

Yes — take the template, not the app. Here's what transfers cleanly:

  • Auth + roles: Google OAuth, JWT validation, 5-tier role system — works for any app
  • Centralized API: Resource+action routing with permission checks — just add your resources
  • Payment pipeline: Stripe PaymentIntent + webhook reconciliation — reusable as-is
  • Email infra: Resend with branded templates, inbound webhook routing — swap the templates
  • Feature flags: feature_registry pattern — add your own flags
  • Brand system: DB-driven colors/fonts/logos — make it per-org
  • CI/CD: GitHub Actions versioning, GitHub Pages deploy — works immediately

What you'd build from scratch: social graph, communities/groups, E2EE messaging, Dion's stateful agent backend, event discovery. None of these exist in the template.

Verdict: Clone alpacapps-infra (not alpacapps), rename the PM tables to your domain model, keep the infrastructure wiring. Faster than starting from zero, cleaner than forking the full app.
How does Dion (a stateful AI agent) fit into the template architecture?

The template's edge functions are stateless by design (Deno cold starts, 150s max execution). Dion needs persistent state, so it should be a separate service with its own Supabase service key — not an edge function.

The template already supports this pattern: the setup guide includes a Hostinger VPS configuration for persistent workers. PAI's Discord bot runs this way in the full app. Dion would follow the same topology:

  • Persistent Node/Python process on a VPS or container
  • Supabase service_role key for DB access
  • Webhook endpoints for inbound events
  • Calls back into edge functions for email/SMS/payment actions
Verdict: The template provides the database + API layer. Dion runs alongside it as a separate service. Clean separation, proven pattern.
What's the lock-in risk with the template's infrastructure choices?

Minimal. Every layer is portable:

  • Supabase: Standard Postgres — dump and restore to any Postgres host
  • Edge Functions: Deno/TypeScript — portable to Cloudflare Workers, AWS Lambda, or any Node runtime with minor changes
  • GitHub Pages: Static HTML — deploy anywhere (Netlify, Vercel, S3, any CDN)
  • R2 Storage: S3-compatible API — swap 4 env vars to move to AWS S3, Backblaze, MinIO
  • Auth: Supabase Auth wraps standard JWT — replaceable with Auth0, Clerk, or custom

The template doesn't use any proprietary Supabase features beyond standard Postgres + PostgREST + GoTrue auth.

Verdict: Zero proprietary lock-in. Every component has a standard migration path.

S Schema & Coupling

Of the 68 Supabase migrations, which are foundational vs. Property Management-specific? Is there a documented "clean base" profile?

There are currently 37 migration files (not 68 — that number may include seed scripts or earlier iterations). They break down cleanly into tiers:

CategoryCountExamples
Core ~6 app_users, property_config, brand_config, feature_registry, release versioning, notification subscriptions
PM-Specific ~20 spaces, assignments, people, time_entries, payouts, vehicle_rentals, Stripe/PayPal/Square, SignWell, identity verification, all IoT device tables (Govee, Nest, Tesla, LG, Anova, etc.), 3D digital twin (PostGIS parcels/structures)
Feature ~11 PAI prompts, image gen jobs, voice calling (Vapi), staff invitation iterations, email compliance cron

There is no documented "clean base" profile. You would need to audit and strip manually. That said, the core layer is small — app_users, auth, brand_config, property_config, and feature_registry are the only tables the shared JS services depend on. Everything else is feature-flagged and could be dropped without breaking the shell.

Verdict: Manual audit required, but the core is genuinely small (~6 tables). You could extract it in a day.
Do PM-specific tables share foreign keys or RLS policies with the core user/community/event layer? Or are they genuinely isolated?

They share FKs, but the coupling is shallow. The main join point is people.id — nearly every PM table (assignments, payouts, vehicle_rentals, identity_verifications, time_entries) has a person_id FK back to people. Similarly, app_users.person_id links auth users to the people table.

IoT device tables (govee_devices, nest_devices, etc.) link to spaces via space_id for location context, but that's optional metadata — not a hard dependency.

RLS is minimal on the client side. Trust enforcement happens in the centralized api edge function via JWT role checks (admin/staff/resident/associate), not through Supabase RLS policies. This means you wouldn't inherit RLS conflicts, but you also wouldn't inherit RLS protections — you'd need to build your own.

Verdict: The coupling is through people and spaces — two tables you'd replace with your own user/community model. No deep RLS entanglement. Clean to separate.
What naming conventions and schema patterns are baked in? Would they conflict with a communities/events/social-graph/E2EE model?

Key patterns baked into the foundation:

Naming: people (not users or members), spaces (not rooms or venues), assignments (not bookings). The people table uses a type enum (tenant, staff, owner, airbnb_guest, associate, event_client, house_guest) — very PM-specific vocabulary.

Patterns: Singleton config tables (property_config, brand_config, pai_config — all id=1). JSONB blobs for flexible config. Centralized API pattern (single /api edge function with resource+action routing). Feature flags via feature_registry.

Conflicts for your model:

  • people assumes physical residents/tenants — you'd want members or profiles for a social platform
  • spaces means rental units — you'd want it to mean community spaces or channels
  • The singleton config pattern (id=1) is inherently single-tenant
  • No concept of "organization" or "community" as a first-class entity
Verdict: The naming would force awkward overloading. You'd spend more time renaming than building fresh. Take the patterns (centralized API, feature flags, JSONB config), not the table names.

G Gemini / PAI

How deeply is Gemini integrated? Is removing it a config swap or a data migration?

Gemini is deeply integrated but has zero stored embeddings or vector columns. No pgvector, no embedding tables. All Gemini usage is real-time inference in edge functions:

PAI chat/voice/emailalpaca-paiReads faq_context_entries, document_index, device tables. Writes to faq_entries (Q&A log)

Email classificationresend-inbound-webhookWrites route_action to inbound_emails

The PAI system (chat widget, voice, Discord bot, email classification) is the deepest integration — it has 15+ tools that call other edge functions for smart home control, data queries, web search. But it's all runtime, not stored state.

Verdict: Removing Gemini is a config swap + deleting edge functions. Zero data migration needed. The faq_context_entries and document_index tables are Gemini-agnostic knowledge stores you could reuse with any LLM.

R Storage

How tightly is R2 bound to Cloudflare infrastructure? Workers-to-R2 direct bindings, or just an S3-compatible endpoint?

It's purely S3-compatible API access. No Workers bindings, no Cloudflare CDN integration, no Workers at all.

The setup:

  • Endpoint: Standard https://<account_id>.r2.cloudflarestorage.com
  • Auth: AWS Signature V4 (standard S3 auth)
  • Helper: supabase/functions/_shared/r2-upload.ts with uploadToR2(), deleteFromR2(), getR2PublicUrl()
  • Config: r2_config table stores account_id, bucket_name, public_url
  • Public CDN: Cloudflare's free pub-*.r2.dev domain (auto-provisioned, not custom CDN config)

Migrating to any S3-compatible service (AWS S3, Backblaze B2, MinIO, Supabase Storage) is literally changing four environment variables and the public URL prefix. No code rewrite.

Verdict: Zero Cloudflare lock-in. Swap the endpoint and credentials, done.

F Fork Posture

How do teams use this — one-time fork or stay on upstream? What's your expectation for significant departures?

AlpacApps is currently a single-operator project, not a framework with downstream forks. The daily versioning (v260710.03 7:35a) reflects continuous development for one production deployment (Alpaca Playhouse). There is no upstream/downstream relationship to manage.

For a team making significant departures (different mobile framework, E2EE, agentic backend), the right approach is:

One-time fork, diverge freely. Specifically:

  • Take the patterns: centralized API edge function, feature flag system, brand/config singletons, webhook ingestion patterns, the shared service layer architecture
  • Take the integrations you need: Stripe payment flow, Resend email (43 templates as reference), Supabase auth setup
  • Drop everything PM-specific: spaces/assignments/people/IoT/vehicles/3D-property
  • Never look upstream again — the velocity here is property-management-focused and will diverge further
Verdict: Fork and diverge. This isn't a framework — it's a production app. Take the wiring patterns, not the domain model.

M Multi-Tenancy

Has anyone adapted this for multi-tenant deployment with strict data isolation?

No. The system is single-tenant by design. There's nascent multi-location support (people.residence_location and spaces.location segregate Cedar Creek vs. Sharingwood), but this is not multi-tenancy — it's one operator managing two properties in one database.

Gotchas if you tried to adapt it:

  • Singleton configs (property_config, brand_config, pai_config — all id=1) assume one property. You'd need to make these per-org.
  • No RLS on client code. Data isolation is enforced by role checks in edge functions, not row-level security. For multi-tenant you'd need proper RLS with org_id on every table.
  • Integration configs are global. stripe_config, telnyx_config, r2_config — all singletons. Multi-tenant would need per-org credential vaults.
  • Edge functions assume single-tenant. The centralized API doesn't scope queries by organization — it trusts JWT roles.

A properties table with property_id FKs is reserved in the schema design but not implemented.

Verdict: Multi-tenancy would be a ground-up rebuild of the data access layer. Don't try to retrofit it — design it from scratch with org_id and RLS from day one.

A Messaging & Agent Architecture

Is there any existing pattern for system/agent senders (not just user-to-user) that could support E2EE messaging with an AI agent?

The scaffold has no real-time messaging system. All communication is notification-oriented:

ChannelPatternDirection
Email (Resend)43 templates, fire-and-forgetSystem → User
SMS (Telnyx)Template-based, logged to sms_messagesBidirectional
Voice (Vapi)Real-time calls, transcripts loggedBidirectional
Discord/TelegramBot bridges to PAI edge functionBidirectional
Notificationsnotification_subscriptions event systemSystem → User

However, PAI (the AI agent) already operates as a system-level sender across all channels. The pattern for "agent sends as itself" exists in the email system (SENDER_MAP.pai defines PAI's from-address), the SMS system (sends from the property phone number), and Discord (bot identity). This is the closest analog to what Dion would need.

But for E2EE messaging with Signal Protocol — that's fully greenfield. Nothing in the scaffold handles key exchange, message encryption, or encrypted storage. You'd need:

  • A dedicated messaging service (not edge functions — you need persistent connections)
  • Key management tables (identity keys, pre-keys, signed pre-keys)
  • Encrypted message storage (opaque blobs, not queryable)
  • Agent key management (Dion needs its own Signal identity)
Verdict: The agent-as-sender pattern exists and is proven. E2EE messaging infrastructure is 100% greenfield.
How would a stateful agentic backend (Dion) fit alongside the scaffold's architecture?

The scaffold runs two agent architectures today that are relevant references:

1. Cloud agents (Supabase edge functions) — stateless, request/response. PAI runs here. Each call gets context from DB, processes, responds. No persistent state between calls. Cost: ~$0.10-0.40/1M tokens (Gemini).

2. Local agents (Alpuca Mac Mini) — Hermes runs as a persistent LaunchAgent service with its own config, tools, and allowed-user lists. Uses local Ollama models (free inference). Has persistent conversation state via filesystem.

For Dion as a stateful agentic backend:

Recommendation: Completely separate service that plugs into Supabase independently. The scaffold's edge functions are stateless by design (Deno cold starts, 150s max execution). A stateful agent needs:

  • Persistent process (not edge functions) — a Node/Python service on a VPS or container
  • Its own service_role key for Supabase access
  • Webhook endpoints for inbound events (messages, triggers)
  • State management (conversation memory, task queues, tool results)

The pattern already exists: PAI's Discord bot (pai-discord/bot.js) runs as a separate persistent service on a Hostinger VPS that calls back into Supabase edge functions. Dion would follow the same topology — separate service, shared database.

Verdict: Separate service, shared Supabase. The pattern is proven (Discord bot, Hermes agents). Edge functions are the wrong host for stateful agents.

! Honest Assessment

If you were building a multi-tenant social platform — events, communities, social graph, E2EE messaging, AI agent — would you still start from this scaffold?

No. I'd take the wiring, not the scaffold.

Here's why, broken down honestly:

What's genuinely valuable to take:

  • Supabase auth + JWT role system — the auth flow, role hierarchy (admin/staff/resident), and JWT validation patterns in edge functions are solid and reusable
  • Stripe payment pipeline — PaymentIntent creation, webhook processing, ledger reconciliation. Battle-tested with real money.
  • Centralized API pattern — single edge function with resource+action routing, permission checks. Clean pattern you'd want anyway.
  • Email infrastructure — Resend setup with inbound webhook routing, 43 branded templates as reference, approval system
  • Feature flag system — feature_registry table + feature-registry.js client-side gating
  • Brand/config system — DB-driven branding (colors, fonts, logos, email templates) that could become per-org
  • Agent-as-sender pattern — proven architecture for AI agents sending across email/SMS/Discord channels

What you'd throw away (and should):

  • The entire PM domain model (people, spaces, assignments) — wrong vocabulary, wrong relationships
  • All IoT/device tables — 63 Govee lights, Tesla vehicles, Nest thermostats. Irrelevant.
  • 3D property digital twin (PostGIS parcels, structures, zoning) — cool but not your domain
  • Singleton config tables — need to become per-org from day one
  • PAI (the AI assistant) — Dion has different personality, capabilities, and architectural needs

What you must build from scratch regardless:

  • Multi-tenant data model with RLS (org_id everywhere)
  • Social graph (follows, connections, groups)
  • E2EE messaging (Signal Protocol key management, encrypted storage)
  • Community/event model (not property/assignment)
  • Dion's stateful agent backend

Bottom Line

  • Take the patterns, not the scaffold. The centralized API, payment pipeline, email infra, auth flow, and feature flags are worth extracting. The domain model is property management — it'll fight you at every turn.
  • Estimated extraction time: 2-3 days to pull out the reusable wiring into a clean Supabase project. Faster than learning where the PM assumptions are buried and working around them.
  • Zero lock-in risk: R2 is S3-compatible (swap endpoint), Gemini is runtime-only (swap model), Supabase is Postgres (portable). The scaffold doesn't trap you.
  • Dion as a separate service is the right call. The edge function layer is stateless by design. Run Dion as a persistent service with its own Supabase service key.
  • E2EE messaging is 100% greenfield. The scaffold has notification patterns, not real-time messaging. Build it clean.
