Reference Guide

Cloud Spend Tokens

How to create read-only tokens for evaluating spend across cloud providers. Follow each step exactly — no admin access is granted.

What these tokens can do

  • View billing data, invoices, and cost breakdowns
  • Read resource lists (servers, databases, storage) — no changes
  • Export cost reports for analysis
  • These tokens cannot create, modify, or delete anything

AWS

Amazon Web Services

5 steps
What you're creating IAM User Access Key — a key pair (Access Key ID + Secret) attached to a user that can only read billing data.
Do this first Someone with root account access must enable IAM billing access: Account Settings → IAM User and Role Access to Billing Information → Activate. Without this, the token won't see any billing data.

  1. Open the IAM console

    Search "IAM" in the AWS console search bar, or use the link below.

    Open AWS IAM Console

  2. Create a new user

    Click Users in the left sidebar → Create user. Name it something like billing-readonly. Do not check "Provide user access to the AWS Management Console".

  3. Attach read-only policies

    On the permissions step, choose Attach policies directly, then search for and select these three policies:

    • ViewOnlyAccess
    • AWSBillingReadOnlyAccess
    • CostOptimizationHubReadOnlyAccess

  4. Create an access key

    After the user is created, click on the user → Security credentials tab → Create access key. Select use case: Third-party service.

  5. Save both values

    Copy the Access Key ID and Secret Access Key. The secret is only shown once. Store both in a password manager immediately.

Tip For org-wide visibility across multiple AWS accounts, use AWS Organizations and grant the user the AWSOrganizationsReadOnlyAccess policy too.
GC

Google Cloud

4 steps
What you're creating Service Account Key (JSON file) — a downloadable credentials file for a non-human account that can only read billing data.

  1. Open Service Accounts

    Go to IAM & Admin → Service Accounts in the Google Cloud Console.

    Open GCP Service Accounts

  2. Create a service account

    Click Create Service Account. Name it something like billing-reader. Add a description like "Read-only access for spend evaluation".

  3. Assign roles

    On the "Grant this service account access" step, add these roles:

    • Billing Account Viewer
    • Viewer (basic role)

    For org-wide billing, grant these at the Billing Account level (not project level) — go to Billing → Account Management → add the service account there.

  4. Download the JSON key

    Click on the new service account → Keys tab → Add Key → Create New Key → JSON. A file downloads — this is your token. Store it securely.

Important The JSON key file is the entire credential — anyone with this file has the permissions you assigned. Treat it like a password.
Az

Microsoft Azure

5 steps
What you're creating App Registration + Client Secret — a three-part credential (Tenant ID, Client ID, Client Secret) for an app identity with read-only billing access.

  1. Register a new application

    Go to Microsoft Entra ID → App Registrations → New Registration. Name it billing-reader. Leave redirect URI blank.

    Open Azure App Registrations

  2. Note the Tenant ID and Client ID

    On the app's overview page, copy the Application (client) ID and Directory (tenant) ID. You'll need both.

  3. Create a client secret

    Go to Certificates & Secrets → New Client Secret. Set an expiry (recommended: 12 months). Copy the Value immediately — it's only shown once.

  4. Assign read-only roles

    Go to Subscriptions → your subscription → Access control (IAM) → Add role assignment. Add both:

    • Reader
    • Cost Management Reader

    Search for your app name (billing-reader) in the members step.

  5. Save your three values

    You need all three to authenticate: Tenant ID, Client ID, and Client Secret. Store in a password manager.

For org-wide access Assign the roles at the Management Group level instead of individual subscriptions to see costs across all subscriptions.

Best Practices

Use service accounts, not personal

If someone leaves the team, a personal token dies with their account. Service accounts survive offboarding.

Rotate every 90 days

Set a calendar reminder. Old tokens are a liability even if they're read-only.

Store in a password manager

Never in Slack, email, or shared docs. Use Bitwarden or AWS Secrets Manager.

Minimum scope always

Only grant billing + basic read access. Don't use admin keys "because it's easier".
