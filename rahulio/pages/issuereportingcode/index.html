Issue Reporting Kit

The in-app Report a bug / Request a feature flow from Bridgit, pulled out so anyone can drop it into their own app: the design, an Android form, an iOS/macOS form and the backend that receives the reports.

How it works

The report is saved on the device first, so nothing is lost on a bad connection. A background job uploads it. The server is idempotent, so a retry never files the same report twice. The team's status changes flow back to the reporter.

The design

One form with a Bug / Feature switch. Each kind keeps its own draft, so switching never loses text. Grouped panels, the Submit button in the top bar, and a clear note on what's sent automatically.

What's on the screen

  1. 1Top bar: ✕ is Cancel; if there is text it asks Keep this draft? (Keep / Discard). Submit is disabled until there's a description, and shows a spinner and “Sending…” while it saves.
  2. 2Bug / Feature segmented switch. Title, intro, label and placeholder all follow it.
  3. 3Description, at least 3 lines, up to 10,000 characters, saved as a draft on every keystroke.
  4. 4Include last screen: the screen the user was on, captured before the form opened (never the form itself; secure windows are skipped).
  5. 5Add screenshot / Add another: the system photo picker, up to 5 pictures in total, shrunk on the device to ≤ 1600 px and ≤ 1 MB JPEG.
  6. 6Include recent log with a count and a Preview of the last 50 entries. Redact anything private before you add it to RecentLog; the kit doesn't.
  7. 7Errors (empty description, 10 reports an hour, a picture that wouldn't load) show in a red banner at the top.

Where users find it

A “Report a bug” and a “Request a feature” row on the More / Settings screen, the overflow menu (⋮) on main screens, and “Report a bug about this” on an item in an activity list. In Bridgit a “My reports” list shows each report's status chip (new, seen, in progress, fixed, won't fix, duplicate) and the team's note. The kit keeps that data on every stored report and pulls it with one call; the list screen itself is yours to draw.

Colours

Material 3 roles: panels use surfaceContainer with a 1 dp outlineVariant border and 16 dp corners; the selected segment uses secondaryContainer; the error banner uses errorContainer with 12 dp corners. Bridgit's values: primary #1F5BD6, surface #F8F9FF, surfaceContainer #E6EBF5, secondaryContainer #FFDEA6, errorContainer #FFDAD6. Wrap the form in your app's own Compose theme (it ships with a plain MaterialTheme); SwiftUI picks up your accent colour automatically.

The API

Six routes. The app identifies itself with an install id and a key it makes once; the server trusts the first key it sees for that id (trust on first use) and stores only the key's SHA-256.

RouteWhoWhat
POST /v1/issuesappFile a bug or feature request. Idempotent on install + client_issue_id: 201 the first time, 200 {"duplicate":true} on a retry.
GET /v1/issues/updates?since=&since_id=appStatus and notes the team changed on this install's issues, after a cursor.
GET /v1/admin/issuesteamNewest first; ?status=&limit=&before=.
GET /v1/admin/issues/:idteamOne issue with its context, log and image links.
GET /v1/admin/issues/:id/images/:nteamA screenshot (JPEG/PNG).
PATCH /v1/admin/issues/:idteam{"status":"fixed","team_note":"Fixed in 1.2.4."}. The reporter sees it on the next updates pull.

Limits & safety

10,000-character text · 5 images · 1.5 MB per image · 10 MB per request · 60 issues an hour per install · 20 new installs a day per address (kept as a keyed daily hash, never the address) · the install, issue and screenshots land in one transaction · team routes need ADMIN_TOKEN · optional Slack/Discord webhook per new report.

Quick start

1 · Backend

cd backend
npm install
npx wrangler d1 create issues
# paste database_id into wrangler.jsonc
npx wrangler d1 execute issues \
  --remote --file=schema.sql
npx wrangler secret put ADMIN_TOKEN
npx wrangler deploy

Free Cloudflare plan is enough. Test locally with wrangler dev and node smoke-test.mjs.

2 · Android

Copy the two .kt files, change the package, set IssueConfig.BASE_URL, add the dependencies in each file's header and the activity to your manifest.

lifecycleScope.launch {
  ReportIssue.open(this@MainActivity,
    IssueKind.BUG, "Settings")
}

3 · iOS / macOS

Add the two .swift files and set IssueConfig.baseURL.

@State var report: ReportRequest?

Button("Report a bug") {
  report = ReportRequest(kind: .bug,
                         screen: "Settings")
}
.sheet(item: $report) {
  ReportIssueView(request: $0)
}
Tested: the backend passes its smoke test under wrangler dev (filing, retry → duplicate, wrong key → 401, bad kind → 400, team list/image/status, updates cursor). The Kotlin compiles (AGP 8.7, Kotlin 2.0, compileSdk 35) and the Swift type-checks for iOS 16 and macOS 13. Neither form has been run on a device in this stripped-down form, so try it on yours before shipping.

What Bridgit adds on top

The kit is the core. Bridgit's own service layers these on; each is a good next step if you need it.

Signed requests

Instead of a bearer key, each install has a P-256 key in the Android Keystore / Secure Enclave and signs every request (method, path, time, nonce, body hash). The server checks the signature, the clock and a nonce table, so a stolen request can't be replayed.

Device attestation

Installs whose key is attested by the platform get higher limits; unverified ones share a daily storage allowance, so new identities can't fill the database.

History both ways

The reporter can confirm a fix or say “Still broken” (also from a notification); the team's agents add comments. Each side syncs with idempotent history ids.

Agents can file too

An AI agent working on the user's device can file a report through the same API, tagged with its name and model.

Automatic repair

Bugs can be handed to an automatic fixer that opens a pull request; the reporter can switch that off per report.

Team triage

Short public references (e.g. M0042), estimates, links between duplicates and a dashboard for the team.
